# 语音日历工具三天开发计划

## 计划目标

本开发计划基于前文已明确的用户需求、核心痛点、MVP 功能范围与技术选型制定，目标是在三天内完成一个可演示、可答辩、主流程完整的语音日历工具原型。

本阶段只交付以下四项 MVP 能力：

1. 语音添加事件
2. 语音查询事件
3. 语音删除事件
4. 事件到期提醒（页面弹窗 + 语音播报）

为了确保项目在三天内可稳定完成，开发过程中不扩展重复日程、多轮对话、多人共享、跨端同步、复杂拖拽编辑等非核心能力。

## 开发前准备

在正式进入 Day 1 之前，应先完成以下准备工作，避免中途被环境问题拖慢进度：

- 确认前后端开发目录结构
- 确认 Python、Node.js、npm、SQLite 本地环境正常
- 准备可用的 API Key
- 如果没有 API Key，提前验证 `FunASR` 或 `Ollama + Qwen2.5` 是否能在本机运行
- 明确前后端接口调试方式，默认使用 `Postman` 或 `Apifox`
- 准备 5 到 8 条测试语音指令，用于全流程联调

建议项目结构如下：

```text
project/
  frontend/
  backend/
  design/
```

## Day 1 — 后端 + 核心 AI 链路（8 小时）

### 当日目标

完成后端基础工程、数据库建模、语音转文字能力接入，以及“自然语言 -> 结构化日程指令”的核心 AI 解析链路，确保新增、查询、删除的后端能力可独立跑通。

### 上午：项目初始化与后端骨架搭建

1. 初始化项目结构，完成前后端分离目录创建
2. 搭建 `Flask` 基础骨架
3. 定义核心路由：
   - `POST /api/voice`
   - `GET /api/events`
   - `POST /api/events`
   - `DELETE /api/events`
4. 配置 `SQLite + SQLAlchemy`
5. 创建 `events` 表

建议数据表字段如下：

```sql
events(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  start_time DATETIME NOT NULL,
  end_time DATETIME,
  description TEXT,
  created_at DATETIME NOT NULL
)
```

### 下午：AI 核心链路打通

1. 接入 `Whisper API`，实现音频上传后返回文字结果
2. 编写 LLM 意图解析 Prompt
3. 将用户文本解析为结构化 JSON
4. 根据解析结果调用后端事件服务，完成新增、查询、删除
5. 用 `Postman` 或 `Apifox` 测通核心接口

建议统一输出结构如下：

```json
{
  "action": "add",
  "title": "组会",
  "start_time": "YYYY-MM-DDTHH:mm:ss",
  "end_time": null,
  "query_range": null,
  "raw_text": "明天下午三点开组会"
}
```

### Day 1 重点实现内容

- 语音文件上传接口可正常接收音频
- STT 服务能稳定返回中文文本
- LLM 能识别三类意图：`add`、`query`、`delete`
- 后端能根据结构化结果正确操作数据库
- 查询接口可返回前端日历所需的事件列表

### Day 1 验收标准

- 上传一段语音后，系统能拿到转写文本
- 输入“明天下午三点开组会”，能成功写入数据库
- 输入“我这周有什么安排”，能返回对应事件列表
- 输入“取消明天的组会”，能删除对应记录

### Day 1 风险与控制

- 风险：语音识别结果不稳定
  - 控制：先用固定测试音频调通，再接实时录音
- 风险：时间语义解析输出格式不统一
  - 控制：Prompt 强制要求返回 JSON，后端加字段校验
- 风险：删除逻辑命中不准
  - 控制：MVP 阶段只支持基于“标题 + 时间范围”的简单匹配删除

## Day 2 — 前端 + 语音交互（8 小时）

### 当日目标

完成前端界面、日历展示、录音交互、语音请求发送、结果展示和语音播报能力，打通“用户说话 -> 后端解析 -> 日历刷新”的主流程。

### 上午：前端基础界面与日历展示

1. 使用 `React + Vite` 初始化前端项目
2. 配置基础页面路由
3. 接入 `Tailwind CSS`
4. 集成 `react-big-calendar`
5. 对接 `GET /api/events`，拉取并展示日历数据

建议页面最少包含以下区域：

- 顶部标题区
- 日历展示区
- 当前操作状态区
- 录音按钮区
- 最近一次语音解析结果展示区

### 下午：录音、播报与提醒能力

1. 使用 `MediaRecorder API` 实现录音模块
2. 完成“按住说话 -> 松开发送”的交互
3. 将录音文件上传到 `POST /api/voice`
4. 根据返回结果刷新日历并提示操作结果
5. 使用 `window.speechSynthesis` 实现 TTS 播报
6. 实现提醒功能：
   - 前端定时器每分钟轮询一次事件
   - 到达提醒时间时触发页面弹窗
   - 同时进行语音播报

推荐播报文案示例：

- “已为您添加明天下午三点的组会”
- “您这周共有三项安排”
- “已取消明天的组会”
- “提醒您，十分钟后有组会”

### Day 2 重点实现内容

- 日历页面能正确展示数据库事件
- 录音交互完整可用
- 语音请求发起后可收到后端解析结果
- 操作完成后前端自动刷新
- TTS 能播报结果与提醒信息

### Day 2 验收标准

- 用户可在页面上完成一次完整录音并成功添加事件
- 查询语音可返回事件结果并在页面展示
- 删除语音可删除已存在事件
- 到达提醒时间后页面弹窗和语音播报都能触发

### Day 2 风险与控制

- 风险：浏览器录音兼容性问题
  - 控制：优先在 Chrome 环境完成演示
- 风险：音频格式与后端接口不兼容
  - 控制：先固定一种浏览器输出格式再适配后端
- 风险：提醒轮询不准确
  - 控制：MVP 以分钟级提醒为准，不追求秒级精度

## 核心 Prompt 设计建议

LLM 解析是本项目的核心环节，Prompt 需要尽量约束模型输出，减少格式漂移。建议要求模型只返回 JSON，不输出解释性文字。

参考 Prompt：

```text
你是一个日历助手，负责把用户的中文自然语言指令解析为结构化日程操作。

请识别用户意图，只允许输出以下三类 action：
- add：新增事件
- query：查询事件
- delete：删除事件

请严格返回 JSON，不要返回任何额外解释。

字段要求：
- action: add/query/delete
- title: 事件标题，没有则为 null
- start_time: ISO 8601 时间，没有则为 null
- end_time: ISO 8601 时间，没有则为 null
- query_range: 查询范围，没有则为 null
- raw_text: 原始文本

当前时间由系统额外传入，请结合当前时间解析“明天”“下周三”“这周”等相对时间表达。
```
