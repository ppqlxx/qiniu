# 语音日历工具数据库表设计说明

## 文档说明

本文档用于说明语音日历工具当前阶段的数据库设计情况，重点回答以下几个问题：

1. 当前项目是否已经设计数据库
2. 当前数据库中有几张业务表
3. `SQLAlchemy 模型`是什么意思
4. `MVP 阶段`为什么只设计一张表

当前项目数据库采用 `SQLite`，后端通过 `SQLAlchemy` 进行表结构定义和数据读写。现阶段数据库并不是随机生成测试数据，而是已经具备真实落库能力，事件的新增、查询和删除都会实际写入本地数据库文件。

## 一、SQLAlchemy 模型是什么意思

`SQLAlchemy 模型`可以理解为：`用 Python 类来描述数据库中的表结构`。

在当前项目中，后端通过定义 `Event` 类来映射数据库中的 `events` 表。模型中的每个字段都对应数据库表中的一列，例如：

- `title` 对应事件标题
- `start_time` 对应事件开始时间
- `end_time` 对应事件结束时间

这样做的好处是，开发时可以直接使用 Python 对象完成数据库的新增、查询、删除，而不需要每次都手写 SQL 语句。

例如，在当前后端代码中：

```python
class Event(db.Model):
    __tablename__ = "events"
```

它的含义就是：

- `Event` 是一个数据库模型类
- `db.Model` 表示它由 SQLAlchemy 管理
- `__tablename__ = "events"` 表示这个类对应数据库中的 `events` 表

因此，在答辩中可以这样解释：

`SQLAlchemy 模型是数据库表在 Python 后端中的对象化表示，我们通过定义 Event 模型来描述 events 表的字段、类型和约束。`

## 二、MVP 阶段是什么意思

`MVP` 是 `Minimum Viable Product` 的缩写，中文通常叫做 `最小可行产品`。

它的含义是：

- 先完成最核心、最必要、最能跑通主流程的功能
- 不在第一阶段扩展大量复杂能力
- 先保证系统能稳定演示和交付，再考虑后续增强

对于这个语音日历工具来说，当前 MVP 阶段只要求完成四项核心能力：

1. 语音添加事件
2. 语音查询事件
3. 语音删除事件
4. 事件到期提醒

因此，在数据库设计上，当前只保留支撑这些核心能力所必须的一张业务表，而不额外设计用户表、权限表、日志表、复杂提醒表等扩展结构。

这也是为什么当前数据库只有一张核心业务表 `events`。

## 三、当前数据库设计概况

当前项目数据库采用：

- 数据库：`SQLite`
- ORM 框架：`SQLAlchemy`
- 业务表数量：`1 张`

当前唯一的业务表为：

- `events`

这张表负责存储日历事件的核心信息，用于支撑语音新增、查询、删除和提醒功能。

需要说明的是：

`当前项目真正设计和使用的业务表只有一张 events 表。`

虽然 SQLite 在底层可能还会有系统内部表，但从项目业务设计角度看，当前数据库结构只有一张核心表。

## 四、events 表设计说明

### 1. 表名

`events`

### 2. 设计目标

该表用于存储用户创建的日历事件，支持后端完成以下能力：

- 保存新增事件
- 按时间范围查询事件
- 删除已有事件
- 为提醒功能提供时间依据

### 3. 字段设计

| 字段名 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `Integer` | 主键 | 事件唯一标识 |
| `title` | `String(200)` | 非空 | 事件标题 |
| `start_time` | `DateTime` | 非空 | 事件开始时间 |
| `end_time` | `DateTime` | 可空 | 事件结束时间 |
| `description` | `Text` | 默认空字符串 | 事件备注说明 |
| `created_at` | `DateTime` | 默认当前时间 | 事件创建时间 |

### 4. 字段含义说明

#### `id`

用于唯一标识一条事件记录，是每个事件的主键。前端在手动删除事件时，会通过这个 ID 调用删除接口。

#### `title`

用于保存事件名称，例如“组会”“面试”“课程签到”等。它是事件最基础的信息之一，因此不能为空。

#### `start_time`

用于保存事件开始时间，是后端进行日历查询、排序和提醒判断的核心字段，因此不能为空。

#### `end_time`

用于保存事件结束时间。当前系统允许该字段为空，因为 MVP 阶段并不强制要求所有事件都具备完整时长信息。如果没有传入，后端也可以在语义处理阶段给出默认结束时间。

#### `description`

用于保存事件备注说明，例如“项目周会”“提前准备汇报材料”等。该字段当前不是必填项，因此默认可以为空字符串。

#### `created_at`

用于记录事件的创建时间，便于后续进行事件管理、调试和可能的扩展分析。

## 五、对应的 SQLAlchemy 模型

当前后端中的 `Event` 模型如下：

```python
class Event(db.Model):
    __tablename__ = "events"

    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200), nullable=False)
    start_time = db.Column(db.DateTime, nullable=False)
    end_time = db.Column(db.DateTime, nullable=True)
    description = db.Column(db.Text, default="")
    created_at = db.Column(db.DateTime, default=datetime.utcnow)
```

这段代码直接定义了 `events` 表的结构，并由 SQLAlchemy 在应用启动时通过 `db.create_all()` 自动创建数据库表。

## 六、等价 SQL 结构说明

如果把当前模型转换为更容易理解的 SQL 形式，大致可以表示为：

```sql
CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  title VARCHAR(200) NOT NULL,
  start_time DATETIME NOT NULL,
  end_time DATETIME,
  description TEXT DEFAULT '',
  created_at DATETIME
);
```

这段 SQL 主要用于辅助理解，实际项目中并不是手动执行该 SQL，而是由 SQLAlchemy 模型自动映射生成。

## 七、这张表如何支撑当前功能

### 1. 语音添加事件

当用户说出“明天下午三点开组会”后，系统会先完成语音识别与意图解析，然后把解析出的事件标题和时间写入 `events` 表，形成一条新的事件记录。

### 2. 语音查询事件

当用户说出“我这周有什么安排”时，后端会根据解析出的时间范围，对 `events` 表中的 `start_time` 字段进行范围查询，并返回符合条件的事件列表。

### 3. 语音删除事件

当用户说出“取消明天的组会”时，后端会根据标题和时间范围从 `events` 表中匹配目标事件，找到后再执行删除操作。

### 4. 到期提醒

前端会定时拉取事件数据，并根据 `start_time` 判断当前是否接近某个事件的提醒时间。因此，当前提醒功能依赖的核心仍然是 `events` 表中的时间字段，而不需要额外单独设计提醒表。

## 八、为什么当前不设计更多表

这是因为当前项目处于 MVP 阶段，开发目标是先保证语音日历的主流程完整可运行，而不是一次性扩展完整的日历平台能力。

因此，以下表结构当前都没有必要引入：

- 用户表
- 权限表
- 操作日志表
- 重复事件规则表
- 独立提醒配置表

对于三天比赛项目来说，当前只保留一张 `events` 表是一种合理的工程取舍：

- 结构简单
- 开发效率高
- 足够支撑四个 MVP 功能
- 更利于答辩时解释系统设计思路

## 九、当前设计的局限性

虽然当前数据库设计已经能够支撑 MVP 功能，但它仍然存在一定局限：

1. 只支持单用户本地事件管理
2. 不支持账号登录和多用户数据隔离
3. 不支持复杂提醒规则配置
4. 不支持事件重复规则
5. 不记录完整的操作历史

这些局限在比赛项目中是可以接受的，因为当前重点是验证语音日历的核心交互链路。

## 十、后续可扩展方向

如果项目后续继续迭代，可以考虑增加以下表结构：

- `users`
  - 用于支持用户登录和多用户隔离

- `reminders`
  - 用于支持更灵活的提醒时间和提醒方式配置

- `operation_logs`
  - 用于记录新增、删除、查询等操作日志

- `repeat_rules`
  - 用于支持每天、每周、每月等重复事件能力

## 十一、结论

当前语音日历工具并不是使用随机测试数据，而是已经基于 `SQLite + SQLAlchemy` 完成了真实数据库设计。

在当前 MVP 阶段，数据库中只设计并使用了一张核心业务表 `events`，这张表已经能够支撑语音添加、语音查询、语音删除和到期提醒四项核心功能。

因此，当前数据库设计是一个围绕主流程、结构简洁、适合三天比赛开发周期的最小可行方案。
