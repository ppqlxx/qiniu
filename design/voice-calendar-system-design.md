# 语音日历工具系统设计

## 文档定位

本文档用于承接前面的用户需求分析和三天开发计划，重点回答系统实现阶段最核心的两个问题：

1. 前后端分别负责什么
2. 四个 MVP 功能如何通过接口、数据流和页面交互落地

本文档面向实际开发，默认后端使用 `Flask`，前端使用 `React + Vite`，系统只覆盖以下四项 MVP 能力：

1. 语音添加事件
2. 语音查询事件
3. 语音删除事件
4. 事件到期提醒

## 我的理解

这个项目的核心不是“做一个完整日历”，而是“把用户的自然语言语音指令，稳定地转换成日历操作”。因此，系统设计的重点不在复杂日历功能，而在以下三件事：

1. 语音录入流程要短，用户说完一句话就能完成操作
2. 后端要把语音内容准确转换为结构化意图
3. 前端要把操作结果和提醒反馈得足够直接

从工程角度看，这个项目的最小闭环是：

`用户说话 -> 前端录音 -> 后端转写 -> LLM 解析 -> 数据库操作 -> 前端刷新与播报`

只要这个链路稳定，比赛演示就成立；其他复杂功能都应让位于这个主流程。

## 系统整体架构

系统采用轻量化前后端分离架构：

`浏览器麦克风 -> MediaRecorder API -> React 前端 -> Flask 后端 -> STT 语音转文字 -> LLM 意图与时间解析 -> SQLite 存储 -> 前端日历展示与语音播报`

### 核心模块

前端模块：

- 录音采集模块
- 日历展示模块
- 操作结果展示模块
- 提醒检测与播报模块

后端模块：

- 语音上传接口
- STT 服务封装
- LLM 解析服务
- 事件服务
- SQLite 数据访问层

外部能力：

- `Whisper API` 或 `FunASR` 负责语音转文字
- `GPT-4o-mini`、`Claude Haiku` 或本地模型负责意图识别和时间语义解析
- 浏览器 `speechSynthesis` 负责语音播报

## 前后端职责划分

### 前端职责

前端只负责交互和展示，不负责自然语言理解。

具体职责如下：

- 使用 `MediaRecorder API` 录制语音
- 上传音频文件到后端
- 展示日历视图和事件数据
- 展示录音中、处理中、成功、失败等状态
- 在操作完成后播放提示语音
- 在提醒时间到达时弹窗并语音播报
- 定时拉取事件数据用于提醒检测

### 后端职责

后端负责所有语义理解和数据操作。

具体职责如下：

- 接收音频文件
- 调用 STT 服务返回中文文本
- 调用 LLM 识别用户意图
- 解析时间表达并标准化为结构化字段
- 根据解析结果新增、查询、删除事件
- 将结果统一封装后返回前端

### 职责边界

为了降低实现复杂度，系统采用以下边界：

- 语义理解只在后端完成
- 时间换算只以后端返回结果为准
- 前端不自己推断“明天”“下周三”等自然语言时间
- 语音删除通过语义匹配完成，不要求前端先拿到事件 ID

## API 设计

系统采用简单 REST 风格，保证三天内可以快速实现和联调。

### 1. POST /api/voice

用途：语音主入口，负责完成语音转写、意图解析和事件操作。

请求方式：

- `Content-Type: multipart/form-data`
- 字段：
  - `audio`: 音频文件

成功响应示例：

```json
{
  "success": true,
  "message": "已为您添加明天下午三点的组会",
  "intent": {
    "action": "add",
    "title": "组会",
    "start_time": "2026-05-30T15:00:00",
    "end_time": null,
    "query_range": null,
    "raw_text": "明天下午三点开组会"
  },
  "data": {
    "event": {
      "id": 12,
      "title": "组会",
      "start_time": "2026-05-30T15:00:00",
      "end_time": null,
      "description": null,
      "created_at": "2026-05-29T21:00:00"
    }
  }
}
```

查询响应示例：

```json
{
  "success": true,
  "message": "您这周共有 3 项安排",
  "intent": {
    "action": "query",
    "title": null,
    "start_time": null,
    "end_time": null,
    "query_range": {
      "start": "2026-05-25T00:00:00",
      "end": "2026-05-31T23:59:59"
    },
    "raw_text": "我这周有什么安排"
  },
  "data": {
    "events": []
  }
}
```

错误响应示例：

```json
{
  "success": false,
  "error_code": "INTENT_PARSE_FAILED",
  "message": "未能识别该语音指令，请重试"
}
```

### 2. GET /api/events

用途：前端拉取事件列表，供日历展示和提醒轮询使用。

查询参数：

- `start`: 开始时间，ISO 8601
- `end`: 结束时间，ISO 8601

成功响应示例：

```json
{
  "success": true,
  "data": {
    "events": [
      {
        "id": 12,
        "title": "组会",
        "start_time": "2026-05-30T15:00:00",
        "end_time": null,
        "description": null,
        "created_at": "2026-05-29T21:00:00"
      }
    ]
  }
}
```

### 3. POST /api/events

用途：手动新增事件，主要用于联调、调试和演示失败时的备用方案。

请求体示例：

```json
{
  "title": "组会",
  "start_time": "2026-05-30T15:00:00",
  "end_time": null,
  "description": "项目周会"
}
```

成功响应示例：

```json
{
  "success": true,
  "message": "事件创建成功",
  "data": {
    "event": {
      "id": 12,
      "title": "组会",
      "start_time": "2026-05-30T15:00:00",
      "end_time": null,
      "description": "项目周会",
      "created_at": "2026-05-29T21:00:00"
    }
  }
}
```

### 4. DELETE /api/events/<id>

用途：按事件 ID 删除事件，主要用于调试、后续扩展或后台手动管理。

成功响应示例：

```json
{
  "success": true,
  "message": "事件删除成功"
}
```

## 统一响应约定

为了简化前端处理，所有接口遵守统一响应结构：

- `success`: 是否成功
- `message`: 给用户看的说明文本
- `data`: 业务数据
- `error_code`: 失败时的错误码
- `intent`: 仅在语音主入口中返回结构化解析结果

推荐错误码：

- `AUDIO_EMPTY`
- `STT_FAILED`
- `INTENT_PARSE_FAILED`
- `TIME_PARSE_FAILED`
- `EVENT_NOT_FOUND`
- `DB_ERROR`
- `INTERNAL_ERROR`

## 数据模型设计

MVP 阶段采用单表即可满足需求。

### events 表

```sql
events(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  start_time DATETIME NOT NULL,
  end_time DATETIME,
  description TEXT,
  created_at DATETIME NOT NULL
)
```

字段说明：

- `id`: 事件主键
- `title`: 事件标题
- `start_time`: 开始时间
- `end_time`: 结束时间，可为空
- `description`: 事件备注，可为空
- `created_at`: 创建时间

## 四个核心流程

### 1. 语音添加事件

1. 用户按住录音按钮说出“明天下午三点开组会”
2. 前端将音频上传到 `POST /api/voice`
3. 后端调用 STT 获得文本
4. 后端调用 LLM 识别 `action=add`
5. 后端解析出标准化时间并写入数据库
6. 后端返回事件数据和成功提示
7. 前端刷新日历并播报“已为您添加明天下午三点的组会”

### 2. 语音查询事件

1. 用户说“我这周有什么安排”
2. 后端解析出 `action=query` 和查询时间范围
3. 后端按时间范围查询 SQLite
4. 返回事件列表和汇总文案
5. 前端展示结果，并按需播报查询结论

### 3. 语音删除事件

1. 用户说“取消明天的组会”
2. 后端解析出 `action=delete`
3. 后端根据标题和时间范围做近似匹配
4. 命中后删除事件并返回结果
5. 前端刷新日历并播报删除成功

实现约束：

`MVP 阶段的删除逻辑采用“标题 + 时间范围”的简单匹配，不做复杂歧义消解。`

### 4. 事件到期提醒

1. 前端定时每分钟请求一次 `GET /api/events`
2. 拉取当前时间附近的事件
3. 前端判断是否进入提醒窗口
4. 命中后弹出页面提示
5. 使用 `speechSynthesis` 播报提醒内容

## LLM 意图解析约定

LLM 的任务不是自由生成文本，而是严格输出结构化结果。

推荐结构如下：

```json
{
  "action": "add",
  "title": "组会",
  "start_time": "2026-05-30T15:00:00",
  "end_time": null,
  "query_range": null,
  "raw_text": "明天下午三点开组会"
}
```

解析要求：

- `action` 只允许 `add`、`query`、`delete`
- 所有时间统一输出 ISO 8601
- 无法识别时返回失败，不猜测用户意图
- 后端对 JSON 做二次校验后再执行数据库操作

## 前端页面理解

为了保证三天内做完，前端页面不需要复杂路由，单页即可完成演示。

建议页面包含以下区域：

- 页面标题区
- 日历展示区
- 当前状态区
- 录音按钮区
- 最近一次语音识别与操作结果区

关键状态建议至少包含：

- `idle`: 等待录音
- `recording`: 正在录音
- `processing`: 正在识别与解析
- `success`: 操作成功
- `error`: 操作失败

## 异常处理设计

系统需要优先处理比赛演示中最容易出问题的场景。

### 前端异常

- 用户拒绝麦克风权限
- 录音为空
- 网络请求超时或失败
- 返回结果为空
- 提醒播报权限或浏览器兼容性问题

### 后端异常

- 音频文件缺失
- STT 服务调用失败
- LLM 未返回合法 JSON
- 时间字段缺失或格式错误
- 删除时未命中事件
- 数据库操作异常

### 异常处理原则

- 后端统一返回错误码和友好文案
- 前端统一显示用户可理解的提示，不暴露技术错误细节
- 识别失败时允许重新录音
- 演示时保留手动新增事件接口作为 Plan B

## 联调与验收场景

至少需要覆盖以下场景：

1. `明天下午三点开组会`
   - 应成功新增事件
   - 应返回标准化时间

2. `我这周有什么安排`
   - 应返回时间范围内的事件列表
   - 若为空，也应返回空数组和友好文案

3. `取消明天的组会`
   - 应命中并删除对应事件

4. 无法识别的语音输入
   - 应返回统一错误码
   - 前端应提示用户重试

5. 到期提醒
   - 到达提醒窗口后应触发弹窗
   - 同时应触发语音播报

## 实现原则

这份系统设计坚持以下原则：

- 主流程优先，避免功能扩张
- 后端统一承担语义理解
- 前端只做交互和结果反馈
- 所有时间格式统一
- 所有异常处理可被演示和解释

对于比赛项目而言，系统的成功标准不是功能最多，而是语音交互主链路稳定、结果清晰、答辩时逻辑完整。
