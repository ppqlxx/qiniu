# 语音日历工具用户需求分析

## 项目背景

传统日历工具虽然已经具备事件记录、提醒和查看等基础能力，但在真实使用场景中，用户仍然需要经历打开应用、选择日期、填写标题、设置时间和提醒等多个步骤，整体录入成本较高。尤其是在通勤、走路、开会间隙、临时想到待办事项等移动场景下，用户往往没有足够时间或不方便进行手动输入，导致很多事项虽然被想到，却没有被及时记录，最终影响日程管理效果。

语音交互能够降低用户记录事项的操作门槛。相比传统手动输入，用户只需要说出一句自然语言，例如“明天下午三点和导师开会，提前半小时提醒我”，系统即可将语音内容转化为结构化日程信息，并完成记录和提醒设置。基于这一点，语音日历工具的核心价值在于提升日历管理的效率和便捷性，让用户能够以更自然、更低成本的方式完成日程管理。

## 用户是谁

本产品的目标用户是日程较多、经常处于移动场景、希望用更低操作成本管理事项的学生和初入职场人群。这类用户并不是没有日历管理需求，而是在实际生活中更容易因为录入流程繁琐、操作不够便捷，而出现“想到事项但没有及时记下”的情况。

结合使用场景，可以将目标用户进一步概括为以下三类：

### 1. 大学生和实习生

这类用户通常需要同时管理课程、作业、会议、面试、社团活动等多类安排，日程来源分散，且临时事项较多。他们主要依赖手机完成信息记录，希望能在较短时间内快速添加事项，因此对语音输入这种低门槛的交互方式具有较高接受度。

### 2. 初入职场的办公人群

这类用户日常需要处理会议、汇报、待办事项、约见安排等工作内容，日程密度较高，且经常处于通勤、会议切换、碎片化办公等场景中。他们更加关注记录效率、提醒可靠性以及快速查看当天安排的能力，希望尽量减少繁琐的手动操作。

### 3. 容易忘事、希望降低记录成本的人

这类用户未必拥有非常复杂的日程安排，但往往存在“想到事情却懒得打字记录”的情况。他们更看重工具是否足够简单、直接，能否以较低使用门槛帮助自己及时记下事项，并在需要时进行提醒和查看。

## 核心需求是什么

本产品的核心需求是帮助用户通过语音这种更自然、低成本的交互方式，完成日程的新增、查询、删除和提醒管理，降低传统日历工具手动输入繁琐、记录不及时、查看不便的问题。

围绕这一目标，用户的核心需求可以归纳为以下几个方面：

### 1. 快速记录日程

用户希望在不方便打字时，直接通过一句自然语言完成事项记录，例如“明天下午三点和导师开会”。这一需求的本质，是减少输入步骤、降低记录门槛，避免因为录入麻烦而错过重要事项。

### 2. 准确理解语音内容

用户不仅需要系统能够识别语音，还希望系统真正“听懂”内容，即从语音中提取出事件名称、日期、时间、提醒时间和备注等关键信息，并转换为结构化日程数据。对于语音日历工具而言，准确理解是功能可用性的基础。

### 3. 快速查看已有安排

用户在使用日历工具时，不只是添加事项，也经常需要查询当前安排，例如“我今天有什么安排”或“明天下午有事吗”。因此，系统需要支持以自然语言形式快速查询日程，并将结果清晰地反馈给用户。

### 4. 方便修改或删除日程

现实中的日程安排经常发生变化，用户会有“把明天的会议删掉”或“把晚上七点改成八点”这类操作需求。因此，系统除了支持新增事项外，还需要支持简单、自然的日程修改与删除能力，以保证日程内容始终准确有效。

## 用户痛点分析

### 1. 手动输入流程繁琐，记录成本高

传统日历工具通常需要用户手动填写事件标题、时间、提醒方式等信息，操作步骤较多。在事项较多或时间紧张的情况下，用户容易因为嫌麻烦而放弃记录，影响后续日程管理效果。

### 2. 移动场景下不方便操作

很多真实使用场景发生在走路、通勤、排队、开会间隙等碎片化时刻，用户虽然产生了记录需求，但并不方便腾出双手完成输入。对于这类场景，传统日历工具的交互方式并不友好。

### 3. 传统录入方式不符合自然表达习惯

用户通常更习惯以自然语言描述自己的安排，例如“后天下午去医院复查”或“周五晚上提醒我交作业”，而不是先拆分日期、时间、标题再分别填写。因此，传统表单式录入方式与用户自然表达习惯之间存在明显割裂。

### 4. 日程查看和管理不够顺畅

除了记录本身，用户还常常需要快速确认“今天还有什么安排”或删除已经取消的事项。如果查询、删除、修改等操作依然依赖多层界面点击，整体使用体验仍然会显得低效，无法真正体现语音交互带来的便捷性。

## 核心用户痛点

这一部分不应在方案设计中被跳过，因为比赛答辩通常会重点追问“为什么必须用语音”“这个产品解决了什么真实问题”。从核心用户的使用场景出发，语音日历工具需要解决的痛点可以归纳如下：

| 场景 | 用户痛点 | 产品方案 |
| --- | --- | --- |
| 开车、做饭、走路等双手被占用的场景 | 用户无法及时打开日历并完成打字记录，容易错过临时想到的重要事项 | 提供全程语音操作能力，通过语音直接添加事件 |
| 记事件时表达模糊，例如“下周三下午开会” | 用户知道自己的安排，但传统日历需要手动换算具体日期和时间，录入成本高 | 通过大语言模型进行时间语义解析，将自然语言转换为结构化事件 |
| 事项变多后容易忘记提醒 | 传统日历提醒方式固定，反馈形式单一，用户容易忽略通知 | 提供页面弹窗提醒和语音播报提醒，提升提醒感知度 |
| 想快速确认未来安排时 | 用户往往需要打开 App、切换日期、翻页查找，过程繁琐 | 支持直接语音查询，例如“我明天有什么安排”或“我这周有什么安排” |

## MVP 功能范围

考虑到项目开发周期只有三天，本项目只实现最核心、最能体现语音交互价值的四项功能，确保主流程完整可演示，不扩展复杂能力。

### 1. 语音添加事件

用户说出类似“明天下午三点开组会”的自然语言后，系统完成录音、语音转文字、时间语义解析，并将事件写入日历。

### 2. 语音查询事件

用户可以直接发出查询指令，例如“我这周有什么安排”或“我明天有什么事”，系统返回对应时间范围内的事件结果，并在页面展示。

### 3. 语音删除事件

用户可以通过类似“取消明天的组会”这样的语音指令删除已有事件。系统需要先解析删除意图，再根据事件标题和时间进行匹配删除。

### 4. 事件到期提醒

当事件接近提醒时间时，系统通过页面弹窗提示用户，并配合浏览器语音播报提醒内容，增强提醒效果。

### 本阶段明确不做的内容

为了控制复杂度，本项目在 MVP 阶段不实现以下功能：重复日程、多轮对话纠错、多人共享日历、跨端同步、复杂拖拽编辑、离线语音识别模型训练。

## 技术选型

### 架构总览

本项目采用“前端采集语音，后端完成识别与语义解析，前端负责展示与播报”的轻量化架构，整体流程如下：

1. 浏览器通过麦克风采集用户语音。
2. 前端使用 `MediaRecorder API` 完成录音，并将音频文件发送给后端。
3. 后端使用语音识别服务将音频转换为文本。
4. 后端调用大语言模型对文本进行意图识别和时间语义解析，输出结构化 JSON，例如 `{ action, title, time }`。
5. 后端使用 `SQLite` 存储事件数据，并根据意图执行新增、查询或删除。
6. 前端接收处理结果后展示在日历视图中，并在提醒场景下调用浏览器 TTS 进行语音播报。

对应链路如下：

`浏览器麦克风 -> MediaRecorder API -> React 前端 -> Flask 后端 -> 语音转文字 -> LLM 解析 -> SQLite 存储 -> 前端日历展示与语音播报`

### 具体技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React + Vite + Tailwind CSS | 搭建速度快，适合三天内完成核心界面和交互 |
| 日历展示 | react-big-calendar | 开箱即用，适合快速实现日历视图和事件展示 |
| 后端 | Flask | 轻量、上手快，适合三天内快速搭建接口并接入 AI 能力 |
| 数据库 | SQLite + SQLAlchemy | 无需额外部署数据库服务，适合比赛快速开发 |
| 语音识别 STT | OpenAI Whisper API | 中文识别准确率较高，集成成本低 |
| 大语言模型 LLM | GPT-4o-mini 或 Claude Haiku | 成本可控，适合做意图识别和时间解析 |
| 语音播报 TTS | 浏览器 Web Speech API | 免费，且无需后端额外部署语音服务 |
| 部署 | 本地演示，或前端 Vercel + 后端 Railway | 适合三天内完成展示和基础部署 |

### 备选方案

如果没有可用的 API Key 预算，可以采用本地免费替代方案：

- 语音识别由 `OpenAI Whisper API` 替换为 `FunASR`
- 大语言模型由云端模型替换为 `Ollama + Qwen2.5`

采用该方案后，系统仍可完成完整演示，但需要额外关注本地模型运行环境和机器性能是否满足要求。
